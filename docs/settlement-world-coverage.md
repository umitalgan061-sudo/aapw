# Settlement World Coverage Contract

## Purpose

The settlement vertical slice is considered covered only when a player can move through an authored settlement, enter an interior, address a functional service, inspect quest/dialogue context, perform a safe trade/craft/travel/rest action, and resume from a checkpoint without introducing a parallel RPG framework.

The runtime ownership remains distributed across the existing systems. This document records the seam used by the additive World Coverage modules so future agents do not accidentally duplicate those systems.

## Canonical services

| Service | Primary role | Primary loop | Secondary loops | Asset evidence |
| --- | --- | --- | --- | --- |
| gate | door | enter/exit | travel | door, road |
| market | vendor | trade | buy/sell/talk | vendor, stall |
| tavern | interior | rest | dialogue/quest | interior, npc |
| blacksmith | crafting | smithing | equipment/trade | forge, workbench |
| farm | survival | interact | rest/travel/trade | field, barn |
| barracks | training | train | quest/equipment | barracks, training |
| stable | mount travel | travel | rest/trade/talk | stable, mount |
| house | persistence | save | rest/equipment | house, bed |

The eight rows are an acceptance vocabulary, not a second service registry. Authored definitions continue to come from `settlementCampaignContent.js` and the existing settlement runtime.

## Playable journey

```text
settlement arrival
    -> gate / door
    -> enterable interior or outdoor service
    -> NPC / vendor / functional station
    -> dialogue / quest context
    -> trade or crafting or training or rest
    -> travel / return
    -> checkpoint
    -> deterministic resume
```

The World Coverage session only orchestrates this sequence. Execution is delegated to the existing runtime handler when a caller provides one. When a handler is absent, the session exposes bounded test doubles only; production callers are expected to inject the existing authoritative handler.

## Asset-first rule

New settlement geometry is not generated by the World Coverage modules. Before a model-bearing change is made, the contributor must inspect the existing asset families and distinguish real source files from LFS pointers.

Relevant families:

- `assets/models/settlements`
- `assets/models/houses`
- `assets/models/props`
- `assets/models/fbx`
- `assets/textures`
- `assets/audio`
- `assets/particles`
- `assets/shaders`

An LFS pointer remains evidence of a source asset. A pointer is not automatically a missing asset.

## Material and placement contract

The shared runtime contract established by PR #584 and merged successor #590 remains authoritative for model-bearing placement. World Coverage code must not implement a second material system.

For new model placement, the required sequence is:

```text
source asset
  -> MaterialAssignmentCore dressing
  -> validateMaterialAssignment
  -> WorldAssetPlacementPipeline grounding/snap
  -> create material/placement manifests
  -> validated scene attach
```

The editor Material Studio stays an authoring/UI concern. It must not be imported by runtime World Coverage modules.

## Surface quality

A building should not be flattened into one generic stone/brown material when source mesh slots allow richer treatment. Where the imported asset supports slots, surface roles should remain separable for wall, roof, wood, door, window, metal and stone trim. Where the source is a single-mesh/single-material asset, layered fallback may be used without destroying the higher-quality authored source material.

Acceptance evidence should distinguish:

- material slots,
- PBR usage,
- texture presence and texture size,
- placeholder count,
- missing material count,
- single-surface risk.

## Grounding and scale

A placed object is valid only when it has a deterministic relationship to the authored ground context. Evidence should include the placement manifest ID, material manifest ID, grounded status, expected ground height, actual ground height, slope and scale.

The acceptance layer treats large vertical error, invalid scale, excessive slope, overlap risk or an attached-but-ungrounded object as a placement failure.

The World Coverage modules never invent terrain or settlement coordinates. Grounding belongs to the terrain/world owner and the shared placement pipeline.

## Quest and dialogue semantics

Quest progress, dialogue condition evaluation, reward mutation and quest persistence stay in the existing QuestSystem/settlement content/runtime layers.

World Coverage presents:

- current objective state,
- available/blocked interaction intent,
- fail-closed reason,
- reward/readiness evidence,
- checkpoint/resume position.

It does not mint a second quest ID space, second dialogue evaluator or second reward ledger.

## Inventory, equipment and economy

Inventory and equipment are caller-owned. Trade quotes, crafting readiness and equipment views are projections only.

An interaction can expose:

- item quantity,
- unit price and total,
- affordability,
- required materials,
- skill readiness,
- equipment slot identity,
- carry/safety context.

Execution must still happen in the existing inventory/economy/crafting runtime.

## Save and resume

Checkpoint data is intentionally small and bounded. It identifies the settlement, current service/node, panel, sequence and metadata. It is not a replacement for the authoritative player save.

The adapter must reject an incompatible settlement checkpoint rather than silently switching the player into another authored settlement.

## Determinism

World Coverage projections are expected to produce stable fingerprints for identical inputs. History, intent queues, receipts and acceptance proof have explicit bounds. A single malformed numeric field must not leak `NaN` or `Infinity` into the public projection.

Determinism is verified in:

- `checkSettlementWorldCoverageSlice.mjs`
- `checkSettlementWorldCoverageRuntimeAdapter.mjs`
- `checkSettlementWorldCoverageContract.mjs`
- `checkSettlementWorldCoverageDeterminism.mjs`
- `checkSettlementWorldCoverageManifest.mjs`
- `checkSettlementWorldCoverageBrowserBoundary.mjs`
- `checkSettlementWorldCoverageApiSurface.mjs`
- `checkSettlementWorldCoverageFreshness.mjs`

## Acceptance proof

A green acceptance proof must be based on shipped/runtime evidence, not an authoring preview alone. The proof schema records service coverage, material manifest quality, placement quality, asset status, camera profiles and interaction history.

For a complete fixture, acceptance should report:

- missing assets: `0`,
- placeholder materials: `0`,
- missing materials: `0`,
- single-surface risk: `0`,
- invalid placements: `0`,
- valid camera evidence,
- monotonic interaction sequences,
- deterministic fingerprint.

Pointer assets are counted separately and preserved as `pointer` evidence rather than converted to `missing`.

## Ownership boundaries

The following remain outside the World Coverage feature:

- combat/player implementation,
- NPC/faction/fauna implementation,
- terrain/environment generation,
- editor Material Studio UI,
- authoritative inventory/economy/crafting state,
- authoritative QuestSystem state,
- authoritative save storage.

World Coverage may bridge these systems through public contracts/events/interfaces, but it must not parallel-rewrite their engines.

## PR gate

Before merge, the PR must be:

1. based on an exact, fresh `origin/main`;
2. within the focused diff budget of `3000` additions+deletions;
3. free of editor/material/terrain/combat/NPC ownership leakage;
4. syntax-clean;
5. deterministic;
6. green on its exact-head workflow/status;
7. rechecked against the current `main` head immediately before merge.

The World Coverage modules are intentionally additive. Their presence alone does not constitute a green shipped-runtime proof; the exact-head CI and the existing runtime acceptance gates remain authoritative.
